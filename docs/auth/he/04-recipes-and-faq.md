# 4. מתכונים ושאלות נפוצות

[→ צד הלקוח](03-frontend.md) · [חזרה לתוכן העניינים](../README.md) · [English](../en/04-recipes-and-faq.md)

## מתכון: שינוי שמות התפקידים לפרויקט שלכם

לכל פרויקט יש שני תפקידים עם שמות משלו. למשל ב־LabSlot יש *סטודנט* ו*אחראי
מעבדה*.

**1. שרת: `backend/src/lib/roles.js`**

```js
export const ROLES = {
  STUDENT: "student",
  LAB_MANAGER: "lab_manager",
};

export const DEFAULT_ROLE = ROLES.STUDENT;

export const authRoles = {
  [ROLES.LAB_MANAGER]: ac.newRole(adminAc.statements),
  [ROLES.STUDENT]: ac.newRole(userAc.statements),
};

export const ADMIN_ROLES = [ROLES.LAB_MANAGER];
```

**2. לקוח: `frontend/src/lib/roles.js`**: אותם ערכים, ובנוסף שמות לתצוגה:

```js
export const ROLES = {
  STUDENT: 'student',
  LAB_MANAGER: 'lab_manager',
}

export const ROLE_LABELS = {
  [ROLES.STUDENT]: 'סטודנט',
  [ROLES.LAB_MANAGER]: 'אחראי מעבדה',
}
```

**3. החליפו את השמות הישנים.** חפשו בשני הפרויקטים את `ROLES.MANAGER`
ו־`ROLES.MEMBER` והחליפו אותם. חפשו בזהירות: קבוע שכבר לא קיים, כמו
`ROLES.MANAGER`, הופך ל־`undefined`, והבדיקה נכשלת בשקט.

**4. עדכנו את `seed.js`** עם משתמשי דמו לתפקידים החדשים, והריצו
`npm run seed`. משתמשים שנוצרו לפני השינוי עדיין מחזיקים את שמות התפקידים
הישנים.

## מתכון: איזה תפקיד מקבל מי שנרשם

את זה קובע `DEFAULT_ROLE`. בדרך כלל זה התפקיד ה"רגיל" (עובד, סטודנט, מדווח).
את התפקיד בעל ההרשאות נותנים דרך ה־seed, או שמנהל נותן אותו בדף *Users*.

**ומה אם ההנחיות אומרות שהמשתמש בוחר תפקיד בהרשמה?** (למשל FoodBridge:
*מפרסם* או *אוסף*.) אף אחד מהם לא חזק יותר, אז זה הגיוני. אל תוסיפו `role`
לטופס ההרשמה, כי Better Auth לא תקבל אותו (בכוונה). במקום זה, הירשמו עם
תפקיד ברירת המחדל ותנו למנהל לקבוע את התפקיד, או שאלו את המרצה איזו גישה הוא
מעדיף. לעולם אל תאפשרו למשתמש לבחור לעצמו תפקיד בעל הרשאות.

## מתכון: יותר משני תפקידים

הוסיפו את התפקיד ל־`ROLES` (בשני הצדדים), ל־`authRoles` ול־`ROLE_LABELS`. אם
הוא צריך לנהל משתמשים, הוסיפו אותו גם ל־`ADMIN_ROLES`. משתמשים בו כמו בכל
תפקיד אחר: `requireRole(ROLES.MANAGER, ROLES.MAINTENANCE)`.

## מתכון: הצגת שם המשתמש ליד רשומה

שומרים את ה־id של המשתמש, ועושים populate בקריאה:

```js
// model
createdBy: { type: mongoose.Schema.Types.ObjectId, ref: "User", required: true },

// controller
const incidents = await Incident.find().populate("createdBy", "name email");
```

בקשו רק את השדות שאתם צריכים (`"name email"`). לעולם אל תשלחו מידע על
סיסמאות. הוא בכל מקרה לא נמצא באוסף `user` אלא ב־`account`.

## מתכון: רשימה נפתחת של משתמשים (למשל "הקצה ל...")

מנהלים יכולים להשתמש בתוסף ה־admin ישירות מהממשק:

```js
const { data } = await authClient.admin.listUsers({
  query: { filterField: 'role', filterValue: 'worker', limit: 100 },
})
// data.users → [{ id, name, email, role, ... }]
```

אם גם **משתמשים שאינם מנהלים** צריכים את הרשימה, הוסיפו נקודת קצה קטנה משלכם,
כי נקודות הקצה של admin מיועדות למנהלים בלבד:

```js
// routes/users.routes.js
usersRouter.get("/", requireAuth, async (_req, res) => {
  const users = await User.find({}, "name email role").sort({ name: 1 });
  res.json(users);
});
```

## בדיקת ההזדהות עם קובצי `.http`

הקבצים `backend/docs/auth.http` ו־`backend/docs/notes.http` מתחילים בהתחברות.
ה־REST Client שומר את העוגייה, ולכן הבקשות הבאות נשלחות כמשתמש מחובר. כדי
לבדוק כמשתמש אחר, הריצו בקשת התחברות אחרת.

בדיקות הזדהות טובות למסמך הבדיקות שלכם:

| בדיקה                                         | תוצאה צפויה |
| --------------------------------------------- | ----------- |
| קריאה לנקודת קצה מוגנת בלי להתחבר             | 401         |
| התחברות עם סיסמה שגויה                        | 401, "Invalid email or password" |
| משתמש רגיל קורא לנקודת קצה של מנהלים בלבד     | 403         |
| משתמש פותח רשומה של משתמש אחר                 | 403         |
| משתמש רגיל פותח דף של מנהלים בלבד             | הפניה חזרה לדשבורד |
| התנתקות, ואז קריאה לנקודת קצה מוגנת           | 401         |

## שאלות נפוצות

### התחברתי, אבל כל בקשה מחזירה 401

- **האם השרת רץ ו־MongoDB פועל?** ה־session נשמר במסד הנתונים.
- **האם אתם קוראים ל־API דרך ה־proxy?** `fetch('/api/notes')` ✅,
  `fetch('http://localhost:3000/api/notes')` ❌ (זה אתר אחר, ולכן העוגייה לא
  נשלחת).
- **האם `BETTER_AUTH_SECRET` השתנה?** כל העוגיות הקיימות הופכות ללא תקפות.
  התחברו מחדש.
- **הרצתם `npm run seed`?** הוא מוחק גם את כל ה־sessions. התחברו מחדש.

### ההתחברות נכשלת עם "Invalid origin" (403)

כתובת ה־frontend לא נמצאת ב־`trustedOrigins`. בדקו ש־`CLIENT_URL`
ב־`backend/.env` זהה בדיוק לכתובת בדפדפן (למשל `http://localhost:5173`, בלי
`/` בסוף).

### שיניתי תפקיד של משתמש, אבל האפליקציה עדיין מציגה את הישן

התפקיד נקרא כשה־session נטען. רעננו את הדף, או התנתקו והתחברו מחדש.

### אפשר לראות את הסיסמה של משתמש?

לא, ואף אחד אחר גם לא יכול. נשמר רק ה־hash (באוסף `account`). כדי לאפס סיסמה
של משתמש דמו, הריצו `npm run seed`.

### כדאי להשתמש ב־JWT במקום?

ההנחיות מאפשרות "JWT **או** session". הפרויקט הזה משתמש ב**sessions**, וזה
עונה על הדרישה במלואה. זה גם פשוט ובטוח יותר לאפליקציית Web: הטוקן נמצא
בעוגיית `HttpOnly` ש־JavaScript לא יכול לקרוא, והתנתקות באמת מסיימת את
ה־session בשרת.

### איפה בודקים הרשאות: ב־router או ב־controller?

| הכלל תלוי ב...                              | בודקים ב...        | דוגמה                      |
| ------------------------------------------- | ------------------ | -------------------------- |
| רק בתפקיד של המשתמש                         | router: `requireRole` | "רק מנהל יכול ליצור אירוע" |
| ברשומה עצמה (בעלים, מוקצה, סטטוס)           | controller, אחרי טעינת הרשומה | "רק הזמנה שלך" |
| בשניהם                                      | בשניהם             | "רק איש תחזוקה, ורק בליקוי פתוח" |

### מספיק לבדוק בממשק?

**לא.** הבדיקה בממשק נועדה לחוויית משתמש נעימה. הבדיקה בשרת היא האבטחה. כל
אחד יכול לשלוח בקשות ישירות ל־API שלכם.

### מה ההבדל בין `useSession()` ל־`getSession()`?

| | `useSession()` | `getSession()` |
| --- | --- | --- |
| סוג | React hook | פונקציה אסינכרונית |
| איפה | בתוך קומפוננטות | `beforeLoad`, loaders, event handlers |
| מתעדכן אוטומטית | כן (רינדור מחדש בהתחברות/התנתקות) | לא, קריאה חד־פעמית |
